# PC Agent 联动使用说明

本功能让手机端与 dshagalt PC Agent 通过共享中继协议进行扫码配对、前台问答、审批和任务同步。手机客户端只负责协议、界面和安全凭证；云中继与 PC 插件由 dshagalt 项目部署。协议原文见同目录的 [`relay-v1-contract.md`](./relay-v1-contract.md)。

公开仓库使用 `RELAY_HOST` 表示已验证中继的部署地址；下文 HTTPS/WSS 地址均为脱敏占位，不能直接用于连接。实际部署地址保留在仓库外的自用构建配置中，不提交到公开源码或文档。

本次用户确认先交付前台 WSS 联动。后台推送保持 `disabled`，应用在后台、锁屏或被系统回收时的及时提醒属于后续配置与验收范围；恢复前台会同步待办。

## 使用前提

1. PC Agent 生成协议二维码。二维码内容是 v1 JSON，包含 `server_base_url`、`pairing_id` 和短期 `pairing_secret`。
2. 正式中继地址在本公开文档中脱敏为 `https://RELAY_HOST`，WSS 为 `wss://RELAY_HOST/v1/ws`，协议 v1。2026-10-05 手机项目任务对实际部署地址从公网复核 `/health`，HTTP 200，系统 TLS 校验成功，返回 `push_provider: disabled`。PC 部署任务交付版本为 `20261005-4`，并报告 Let's Encrypt IP 证书及续期 dry-run 通过；手机项目没有修改服务器。客户端继续严格验证证书，不改用 HTTP。
3. PC 端和手机端需采用同一份 v1 协议、事件名和字段。二维码过期、被使用、被拒绝或设备撤销后，需要重新配对。

## 扫码绑定

当前入口先打开聊天页。左上历史侧栏底部的“配对与联动管理”可进入下述扫码、设备、任务和通知管理。桌面历史读取及聊天操作见 [PC-Agent聊天与历史.md](PC-Agent聊天与历史.md)。

1. 在 Windows 桌面应用中打开“更多 → 设置 → 通用设置 → 手机联动”，生成新的有效期 300 秒、单次使用的配对二维码；在手机应用中打开“设置 → PC Agent 联动”。二维码只在本机配对界面使用，不把 secret 或设备 token 发到聊天。
2. 点击“扫码绑定”，允许相机权限后扫描 PC Agent 显示的二维码；也可以粘贴完整 JSON 作为故障排查方式。
3. 应用会显示二维码中的服务器地址。确认地址可信后，点击“信任并申请配对”。二维码不含 PC 名称；PC 确认后再显示已绑定 PC。客户端只接受 HTTPS、无路径/查询参数的 origin，并校验协议版本、UUID 和 64 位十六进制配对密钥。
4. 手机先在独立安全存储中生成并保存设备 ID 和高熵设备 token，再提交配对申请。短期 `pairing_secret` 不落盘、不写日志。
5. 等待 PC Agent 明确批准。状态变为“已绑定”后，手机才会建立 WSS/REST 业务连接。PC 可通过确认时的可选 `capabilities` 收紧权限，手机不自行扩大权限。应用重启后会从安全存储恢复待确认配对并继续查询状态。
6. 页面中的“解绑”会撤销已确认的当前手机凭证、断开连接并清除本地联动数据。尚待确认的配对需先在 PC 拒绝或等待过期后同步。要绑定另一台 PC，请再次扫码建立独立 profile，不会覆盖已有 PC 的凭证。

## 前台提问与审批

PC Agent 创建问题或审批时，手机在应用处于前台时显示应用内卡片，卡片包含 PC、会话、问题正文、期限和输入类型：文本、单选或多选。多个待办按顺序排队，每个问题只弹出一次。

请在期限内明确提交回答或批准/拒绝。提交使用稳定 `action_id`，网络重试不会产生重复动作。界面会区分“发送中、等待 PC、已接受、被拒绝、过期、冲突”等状态；HTTP 202 或“消息已送达”只表示中继收到动作，不等于 Agent 已接受。PC/其他客户端已经处理、取消或过期时，手机卡片会自动关闭或更新。

应用在后台或锁屏时不会强行覆盖其他应用。恢复前台后会先补拉并校准待办，再决定是否显示卡片。

## 下发和取消任务

在“PC Agent 联动”页面选择目标 PC、已授权工作区和会话，打开“新任务”，输入任务内容后点击发送。任务必须由用户明确点击确认，不会由角色对话或语音自动触发远程控制。任务状态来自 PC 的真实回执，显示排队、运行中、成功、失败、取消、离线或未知。

取消任务时选择对应会话和任务 ID，点击“取消任务”并确认。手机会重试同一个 `action_id`；最终是否取消以 PC 的 `action.result` 和后续 `task.updated` 为准。

## 断网、重连与数据恢复

客户端把每个 PC 的 profile、连续事件游标和未完成 action outbox 持久化。断网后会使用指数退避重连，并从最后一个已确认的连续游标补拉事件；事件按 `event_id` 去重，只有成功落盘后才发送 ACK。

如果服务器返回 `CURSOR_EXPIRED`，客户端获取 `/v1/state` 一致性快照，保存快照游标后从该位置继续补拉，不会直接清零游标而漏掉待办。设备被撤销时会断开连接并清理凭证，需要重新扫码。

手机读取单个事件时解析正式接口的 `{event: EventEnvelope}` 包装，并核对事件 ID 和 PC。`ActionSummary.request` 是目标 PC 专用的动作恢复信息；手机使用自己的安全 outbox，不缓存或使用该字段。每次同步会刷新 PC 授予的权限，权限收紧后停止对应问题提交和动作重试。

## 后台推送与厂商渠道

前台联动和断线补拉不依赖推送。后台、锁屏或进程被系统回收后的及时提醒，需要中继服务和手机厂商推送平台均已配置。推送只携带 `event_id`、`pc_id` 和事件类型等最小信息，点击通知后应用再通过鉴权 API 读取正文；WSS、推送和补拉使用同一套事件去重。

当前代码预留以下 provider：

- `fcm`：需要 Firebase Android 项目公开标识（API key、App ID、Sender ID、Project ID），并在真实设备和服务端验证通知通道。
- `huawei`、`xiaomi`、`oppo`、`vivo`、`honor`：需要在 Android 宿主安装对应厂商 SDK，并由 `RelayPushBridge` 接入真实注册/回调。
- `jpush`、`getui`：需要对应聚合 SDK、应用凭证和服务端发送配置。

当前正式中继的推送 provider 为 `disabled`，尚未完成后台推送。未提供真实 SDK、项目配置或服务端凭证时，手机 provider 会返回“未配置/不可用”，不会伪造 registration token；本地通知、测试 transport 或前台补拉不能标记为真实后台推送成功。Android 13 及以上还需要用户授予通知权限。

示例构建配置见 [`push-config.example.json`](./push-config.example.json)。只放公开项目标识，不要放设备 token、`pairing_secret`、Authorization、厂商私钥或服务端密钥。加密构建脚本会拒绝未列出的字段。

## 安全和排障

- 不要把二维码、设备 token、推送 registration token 或完整 Authorization 截图、提交到仓库或导出到聊天备份。
- 服务器地址必须来自用户确认的二维码；客户端不会静默信任新的地址，也不会接受公网明文 HTTP 或任意证书。
- 正式中继 HTTPS 健康与系统 TLS 信任已验证。该验证只证明公网服务入口可达，不能代替手机扫码、PC 批准、前台问答、PC 接受以及任务完成的实际联调；Android 设备上的证书信任仍需真机验证。
- 若页面显示“前台同步可用、后台推送未配置”，仍可在打开应用后刷新并处理问题；锁屏及时提醒要等真实推送渠道完成配置和真机验证。
- 网络错误、配对过期、拒绝、设备撤销等状态会显示为可读中文；必要时重新生成二维码并重新绑定。

## 开发测试 transport

测试 transport 只用于 Flutter 单元/组件测试，服务地址、事件和状态均为本地构造数据。它不能替代真实中继、PC Agent 或厂商推送验收。PC 任务已报告真实 Loader/HTTPS/WSS 与手机协议测试客户端的问答及任务链路通过，仅模拟 LLM；实体 Flutter App 仍需执行“PC 提问 → 手机前台弹窗 → 手机回答 → PC 接受 → 任务完成 → 手机下发新任务”的双端验收。测试手机已撤销，实体手机需扫码创建独立身份。后续启用后台推送时，再在实际无 Google 服务设备上验证相应厂商渠道。
