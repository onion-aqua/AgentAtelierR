# AgentAtelierR 自托管更新方案

设计日期：2026-10-19。用户已选择“完全自托管，接受代码更新时由 Android 确认安装”。本文保留完整设计；当前已实现的范围和验证边界见 [实施说明](SELF_HOSTED_UPDATE_IMPLEMENTATION.md)。尚未构建引导版本或部署云服务。

## 1. 确定的更新方式

采用“资源热更新 + APK 增量更新 + 全量更新”三条路径，共用一个启动提示和版本中心。

| 内容 | 更新方式 | 用户感知 |
| --- | --- | --- |
| 已纳入资源管理层的图片、音频、加密角色包、动作目录、默认提示词数据 | 下载目标快照中缺少的资源，校验后切换资源版本 | 无需安装 APK；需要重载场景时征求同意，或在下次启动生效 |
| Dart UI、TTS/记忆/聊天等业务代码，Android Kotlin/Java、插件、Spine 原生库、权限、Flutter SDK | 下载与当前安装包精确匹配的差分，在本地重建完整目标 APK，然后调用系统覆盖安装 | 节省下载量；Android 要求用户确认安装，安装后重新打开 |
| 没有匹配差分、差分过大、应用来源/签名不兼容、用户选择完整版 | 下载完整目标 APK，校验后调用系统安装 | 完整包下载与系统安装确认；不兼容签名不能强行覆盖 |

标准 Flutter Release AOT 无法通过普通资源 ZIP 替换任意 Dart 代码。以上第二条称为“APK 增量更新”，界面使用“立即更新”，不标成“无需安装的代码热更新”。本方案不引入第三方代码热更新引擎。

## 2. 当前项目核查结论

- 当前 Android 显示版本为 `1.0.4.1`，内部 build 为 `46`。没有现成更新器、远程代码补丁引擎、APK 安装桥接或安装来源权限处理。
- 只读检查现有 build46 APK：649,231,463 字节。其中 ZIP 内普通 Flutter 资源约 476.19 MiB，加密角色资源约 85.58 MiB；资源占包体的大部分。实际差分大小必须用真实构建测量，不能提前承诺每次只有几 MB。
- 当前只有 GitHub remote `onion-aqua/AgentAtelierR`，没有发现 Gitee 仓库配置。
- 当前 release 构建选择了 debug signing config。首次引导版及后续覆盖包必须核对并保持与用户已安装包兼容的实际证书；不能在接入更新器时直接换签名导致无法覆盖。正式签名迁移单独规划。
- 用户提供的服务器对话包含既有 Nginx / PC Agent 服务和 HTTPS 运维记录。本次仅读取对话，未连接服务器；历史运行状态不等于当前状态。后续部署需要现场核验，更新服务采用独立目录和路由。

**首次必须完整安装一次“带更新器的引导版”。** 已经发布且没有更新检查代码的旧包，无法凭空弹出新更新提示。引导版安装完成后，才进入自动检查和增量更新流程。

## 3. 启动提示与操作

启动检查在应用成功加载到可交互界面后异步进行，不阻塞启动；不在启动遮罩、扫码配对、PC Agent 问题弹窗上叠加更新框。

```text
┌──────────────────────────────────────┐
│ 发现新版本                         × │
│ AgentAtelierR 1.0.4.5                │
│ 当前版本：1.0.4.1                    │
│                                      │
│ 更新内容                             │
│ · 从 Gitee Release 同步的更新说明     │
│ · 可滚动，显示更新、使用方法、注意事项 │
│                                      │
│ 预计下载：按实际更新计划显示           │
│ 本次含程序更新，随后需确认系统安装     │
│                                      │
│ [GitHub 自行更新]     [立即更新]       │
│            下载完整安装包             │
└──────────────────────────────────────┘
```

- 右上角 `×` 和系统返回均可关闭，不强制更新，不妨碍继续聊天。
- “GitHub 自行更新”用外部浏览器打开该版本对应的 Release 页面。
- “立即更新”自动选择资源更新、匹配的 APK 差分或完整版，并显示真实下载量、进度、校验和安装状态。
- “下载完整安装包”始终保留；设置中的“关于 / 检查更新”也保留三个入口。
- 关闭后本次运行不重复弹窗；同一 `release_id` 建议默认静默 24 小时，手动检查不受限制，发布新的 `release_id` 可再次提示。
- 用户取消系统安装后保留已校验的目标包，显示“继续安装”；不循环拉起安装器。
- 下载中可以关闭提示，重新进入版本中心查看；更新执行使用单任务锁，防止重复点击创建多个下载。
- 代码更新前保存对话、存档、待提交动作；提示安装会重启应用。资源切换不能在播放动画、合成语音或修改存档中途强行进行。

## 4. Gitee 优先与 Release 更新说明

默认提供商为 Gitee。客户端先读取配置的 Gitee 更新入口和对应 Release 信息；失败后读取自托管服务的已缓存元数据，再尝试 GitHub。用户可以在更新设置中切换来源。

云端定时任务同步 Gitee Release，备用读取 GitHub Release，缓存标题、正文、发布时间和手动下载链接。Gitee API 如需令牌，令牌只放服务器，不放 APK。

更新框使用 Release 正文的 Markdown 文本，不执行网页 HTML 或脚本；正文用于展示，不能从正文中的任意链接或代码片段推断“应安装哪个包”。安装文件、hash、版本兼容和下载来源由签名机器清单决定。

Gitee 与 GitHub 同步有延迟时，按 `release_id` 对齐：可以展示“此版本说明暂未同步”，不能把旧版本说明误标成新版本。网络失败时正常打开应用，可展示上次成功查询时间。

目前还需要提供实际 Gitee 仓库 URL；设计阶段不创建仓库或擅自镜像用户代码。

## 5. 版本标识不能只看版本文字

分开记录以下标识：

| 标识 | 作用 |
| --- | --- |
| `display_version`，例如 `1.0.4.5` | 展示给用户，按四段整数解释，不转浮点数 |
| `release_seq` / `release_id` | 每次发布不可复用的序号与身份；资源更新也递增 |
| `native_build` / Android `versionCode` | 每次发布新 APK 严格递增，覆盖安装的原生版本依据 |
| `apk_sha256`、包名、证书、ABI | 选择精确差分基线，校验本地重建结果 |
| `runtime_compat_id` / `resource_api_version` | 表达运行时、原生插件与资源读取协议的兼容能力，不只比较版本文字 |
| `resource_snapshot_id` | 当前激活的完整资源快照及兼容范围 |
| `updater_protocol_version` | 防止旧更新器误读新清单或补丁格式 |

过去多次覆盖同一个 Release、相同版本文字甚至相同 build，可能对应不同 APK。因此 `1.0.4.1 + build46` 仍不足以确定差分基线，需要读取当前安装 APK 的 SHA-256 或精确发布指纹。计算 hash 在后台进行，并按安装时间等缓存失效条件复用结果。

以后可以继续使用一个熟悉的 Release 展示页，但每个实际发布必须有新的 `release_seq`；APK、差分和资源对象以唯一 ID/hash 保存，不覆盖已经发布的字节。`latest` 仅作为指向最新版的可更新入口。

## 6. 跨版本：从 1.0.4.1 直接到 1.0.4.5

### APK 差分

每个差分绑定：`base_apk_sha256 → target_apk_sha256`。它描述从该完整基线到目标版本的全部差异，不是“最新一次提交的改动”。

| 当前安装包 | 最新目标 | 处理方式 |
| --- | --- | --- |
| 已收录的 1.0.4.1 精确包 | 1.0.4.5 | 下载直接的 `1→5` 差分，重建完整的 1.0.4.5 APK |
| 已收录的 1.0.4.2 精确包 | 1.0.4.5 | 下载直接的 `2→5` 差分 |
| 1.0.4.1 同名但不同 hash 的包 | 1.0.4.5 | 不能套用错误基线；查找该 hash 对应差分，没有则下载完整版 |
| 很老或未记录的版本 | 1.0.4.5 | 下载完整 1.0.4.5，数据按迁移规则升级 |
| 用户只缺少最新资源 | 1.0.4.5 兼容资源快照 | 下载目标快照缺失对象，校验后一次切换 |

**不把 `4→5` 差分交给 `1` 版本，也不要求用户依次安装 2、3、4。** 服务器为支持范围内的历史精确基线生成直达最新版的补丁；超过保留范围时走全量。这样保证升级内容完整，但不承诺所有年代的版本都能只下载小补丁。

建议首版保留最近 6 个 APK 基线和明确的长期基线，参数可调整。旧差分、旧资源对象只能在确认没有仍受支持的清单引用后清理。

### 资源完整快照

目标清单列出最新版所需的全部受管理资源及其 hash。客户端按目标清单计算缺失对象：

`需下载 = 目标快照全部对象 − 本地已校验对象`

旧版本中已存在且 hash 相同的对象复用，新对象下载；目标快照不再引用的资源在新版本健康确认后回收。因此跳过多个资源版本也能补齐全部变更与删除。

程序与资源有兼容约束。若新资源要求新代码，应先准备完整资源快照、安装兼容 APK，再激活资源；旧代码不得提前加载新 schema / 新 Spine 格式。

## 7. APK 增量技术

优先评估 HDiffPatch 的流式二进制差分与原生 patch 库。直接对已签名完整 APK 生成补丁，手机端流式重建，结果必须与目标 APK **逐字节完全一致**。不在手机端重新签名，也不选要求预先改签 APK 的优化模式。

原生 patch 库要随引导版一起集成，覆盖项目支持的 ABI。补丁格式和 patch 库兼容版本进入清单。对 Android split APK、渠道重打包、ABI 不一致等情况单独识别；首版只对已识别的项目单 APK 发布包生成差分，其余走正确渠道/ABI 的完整包。

差分在发布电脑或 CI 离线生成和验证，云服务器只分发；避免在已有其他服务的小服务器上进行高内存 APK 差分计算。

发布前用真实 APK 对比：补丁大小、低内存设备重建耗时、峰值内存、耗电和额外磁盘。若补丁接近完整包大小，例如达到配置阈值 75%，直接提供完整版更合适。阈值是待测策略，不是已经验证的节省比例。

Android 需实现 FileProvider、`REQUEST_INSTALL_PACKAGES`、安装来源授权及系统安装流程。覆盖安装保留应用数据，不先卸载旧应用。厂商系统可能增加安全检查或安装确认，应展示引导，不能绕过。

即使差分很小，手机仍需为目标完整 APK、补丁临时文件和系统安装过程准备足够磁盘空间；下载前检查并给出可理解的空间需求。

## 8. 加密资源与下载效率

当前保护脚本每次都会重新 AES-GCM 加密全部角色包。随机 nonce 会让未改变的原始资源也产生不同密文，降低跨版本复用和差分效率。

必须加入构建缓存：

`缓存键 = 明文内容 hash + packId + keyId + 资源格式版本`

内容和密钥版本不变，复用之前验证过的完整加密对象；内容改变时，使用新的安全随机 nonce 重新加密。**不能通过固定或重复使用 nonce 来追求稳定差分。**

远端只分发加密角色资源和允许公开的资源。资源密钥、签名私钥和私有服务器配置不进 GitHub/Gitee 仓库、更新清单或日志。现有不允许上传仓库的角色/服装规则继续适用。

第一阶段可以先复用加密对象并提供 APK 差分；第二阶段把大体积可选资源进一步从基础 APK 分离，在云端按需下载。全量“离线资源包”作为独立下载保留，不能在没有资源的情况下宣称基础包可完整离线使用。

## 9. 客户端模块与接入点

新增独立更新模块，避免混入 LLM、角色记忆或 PC Agent 消息协议：

- `UpdateService`：启动/前台节流检查、版本比较、计划与状态。
- `ReleaseSource`：Gitee、云端缓存、GitHub 适配，文案与下载计划对齐。
- `UpdateManifestVerifier`：签名、schema、渠道、平台、ABI、兼容范围验证。
- `UpdateDownloader`：断点续传、镜像、hash、磁盘检查及进度。
- `ResourceUpdateStore`：内容对象、暂存快照、原子激活、旧资源回退。
- `ApkUpdateInstaller`：原生差分、目标 APK hash/签名/版本核验、安装器桥接。
- `UpdateDialog` / 版本中心：非强制提醒、GitHub、自动更新、全量下载。

具体接入：

- `lib/main.dart`：启动初始化；首屏和启动遮罩结束后安排提示。
- `lib/src/app_shell.dart`：全局调度和生命周期恢复检查；与现有 PC Agent 弹窗排队，不抢占。
- `lib/src/protected_character_assets.dart`：在 `rootBundle` 前增加已校验的资源版本读取层，切换后清缓存。
- 动作 JSON、地图、图片和音频读取：统一资源 resolver 和资源枚举；只替换 `DefaultAssetBundle` 不够，因为当前存在直接 `rootBundle`、`AssetSource` 和 `AssetManifest` 调用。
- `tool/build_protected.ps1`：继续作为唯一保护构建入口，增加缓存、版本元数据和更新发布产物，不另开裸 `flutter build` 路径。
- `tool/publish_github_release.ps1`：扩展唯一产物命名与更新元数据发布；保留全量 APK / Windows ZIP。

## 10. 自托管服务

建议在所提供服务器上使用独立更新目录和 HTTPS 路由，例如以下占位地址：

```text
https://updates.example.com/agentatelier/
  channels/android/stable.json
  channels/windows/stable.json
  releases/<release_id>/manifest.json
  releases/<release_id>/notes.md
  objects/<sha256>
  apk/<target_sha256>.apk
  delta/<base_sha256>/<target_sha256>.patch
```

以上仅是命名草案，不是已经部署的服务。真实地址通过本地私有构建配置注入；公开源码只保留模板，不写入用户服务器 IP 或凭据。

- 静态 HTTPS 服务分发文件，支持 Range / ETag / 断点续传。
- 更新清单短缓存，按 hash 命名的对象长期不可变缓存。
- 轻量同步任务获取 Release 正文和渠道指针；无需把大资源或差分放进业务数据库。
- 不承诺 Gitee 适合作为大文件 CDN；下载优先自托管静态地址，可配置经过验证的镜像和 GitHub 备用链接。
- 若服务器带宽不足，后续可将加密对象放到国内对象存储/CDN，更新调度和签名仍自托管。
- 更新任务有独立目录、服务配置和资源限额；部署前确认现有反向代理和端口，不能停止 PC Agent 等现有业务来腾位置。

## 11. 机器清单与发布顺序

清单采用版本化签名结构，至少包含：

```text
签名负载：
  schema_version, release_id, release_seq, display_version
  channel, platform, updater_protocol_version, published_at
  target_apk: versionCode / packageName / ABI / sha256 / certificate / urls / size
  apk_deltas[]: base_sha256 / target_sha256 / format / patch_sha256 / urls / size
  resource_snapshot: id / schema / compatible_runtime_ids / asset_key_id / manifest_hash / url
  notes: release_id / gitee_url / github_url / cached_markdown_url
  revoke / rollback 等显式管理信息（限定资源回退权限）
签名：
  key_id, algorithm=Ed25519, signature
```

这是设计字段，实施时需冻结成正式 schema、规范化签名字节和测试向量。客户端预置受信任公钥；私钥离线或保存在受限发布环境。HTTPS、SHA-256 和签名各自承担传输、完整性和发布者认证，不能只靠一个普通 hash。

发布顺序：保护构建一次 → 保存完整 APK 和符号 → 生成历史基线到目标的差分 → 在本地逐一重建并校验 → 上传不可变文件和资源 → 发布/同步 Release 正文 → 发布签名版本清单 → 最后原子切换渠道 `latest` 指针。

上传失败不能提前让客户端看到指向缺失对象的版本。Release 文案修改不自动获得执行权限；撤回有问题的资源需要新的有效签名指令。已信任的发布序号要持久化，避免镜像旧缓存让客户端错误降级。

## 12. 数据迁移、异常与回退

- 用户存档、长期记忆、NPC 联系人/消息、API 凭据、用户壁纸/音色和本地模型独立于更新对象目录。更新清理仅操作受管理缓存，不能递归清理用户数据目录。
- 数据升级以 schema 为准，迁移逐级执行且幂等，例如 `schema1→2→3→4`；允许程序版本一次跨越多版。迁移前备份，成功后提交新 schema。
- 新版本首次启动运行健康检查：关键配置可读、资源可解密、存档可打开。资源快照故障可以自动切回上一已验证资源版本，保留安装包内的最低资源回退。
- APK 安装前，补丁失败、hash/签名失败、断电或网络中断均不替换当前应用。断点文件可恢复，校验失败可换镜像或明确回退全量。
- APK 安装后，Android 不保证允许降级安装。不能承诺“自动装回旧 APK”；程序问题应发布更高 `versionCode` 的修复包，必要时让该修复包恢复旧业务实现。数据迁移应为这一恢复保留兼容窗口。
- 没有网络、用户关闭更新、安装被取消、安装权限未授予，都不阻止使用已有版本。

## 13. Windows 同步方案

共用版本提示、Gitee/GitHub 文案和签名清单。Windows 发布目标是完整目录快照，下载缺少/变化的 EXE、DLL、`data/app.so` 和资源文件。

更新 helper 必须随首次引导版提供并纳入签名校验。应用退出后，helper 在受控目录原子替换文件、保留上版程序目录并重启；不能运行中直接覆盖正在加载的 DLL。新旧目录切换失败时恢复原程序。全量 ZIP 保留，用户数据目录与安装目录分离。

Windows 文件级差异更新可以节省传输，也不等同于运行中无感替换所有代码。

## 14. 分阶段实施与验收

### 第一阶段：可用的自托管更新器

完成启动提示、Gitee 优先/降级来源、GitHub 手动入口、全量下载和系统安装；接入精确 APK 差分、服务器静态分发、保护资源构建缓存。发布首次完整引导版。

### 第二阶段：资源热更新

建立统一资源读取层、完整资源快照、加密对象分发、原子切换和健康回退；将常改动的动作目录、默认提示词、商店图和可选角色资源逐步纳入。

### 第三阶段：Windows 文件增量与运维

完成 Windows helper、发布自动化、镜像、下载统计和灰度渠道；统计不上传聊天正文、模型 Key 或存档。

主要验收用例：

1. 从不同精确基线的 1.0.4.1 / 2 / 3 / 4 一次升级到 1.0.4.5，结果 APK hash 均等于同一目标，目标功能与资源完整。
2. 同名同 build 不同 APK hash、未知来源 APK、split APK 和 ABI 不匹配不会误套补丁。
3. Gitee 超时、限流、没有新正文时正常降级，并按 release_id 展示对应说明；离线不阻塞启动。
4. 用户点击 `×`、返回、GitHub 或取消安装均能正常继续使用应用，不重复抢占 PC Agent 问题弹窗。
5. 下载中杀进程、断网、磁盘不足、文件损坏和签名伪造时，不破坏现有应用与数据。
6. 资源跨版本新增/变更/删除完整；坏快照可回退；缺失资源时有可用错误提示与恢复入口。
7. 存档和记忆 schema 跨多版迁移、迁移中断重跑、资源回退后的存档打开均有测试。
8. 在实际小米/红米、OPPO/一加、vivo、华为/荣耀、三星等可取得设备上验证安装授权与确认流程，不能只用模拟器宣称厂商适配通过。

## 15. 实施前还需落实

- Gitee 仓库及对应 Release 入口；是否与 GitHub 同步公开代码按用户既有资源限制执行。
- 更新用受信任 HTTPS 地址、有效证书、服务器可用磁盘与带宽；从对话中的既有服务器核查后确定。
- 首个引导版版本号、递增 versionCode、已安装签名指纹和需要继续支持的历史 APK 原文件。
- 真实旧/新保护构建的差分体积和手机重建性能基准。
