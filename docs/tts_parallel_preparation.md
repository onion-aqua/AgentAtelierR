# TTS 并行准备与顺序播放

更新日期：2026-10-22。当前为源码实现，未重新打包、安装或发布。

## 行为

| 入口 | 准备与播放 |
| --- | --- |
| 普通聊天 | 首次提交前两段；音频按原段落顺序播放，播放期间继续准备后续段落，最多两路准备任务。 |
| 持续 ASMR | 最多两路准备任务；待播放音频与正在准备的片段合计最多三段，播放释放空间后补充。 |
| 虚拟电话 | 已生成的句子最多提前启动两路流；当前句仍可边接收边播放，后一流等待轮到自己。当前句播放排空后才补入更后面的句子。 |
| 设置试听 | 单段文本只发一次生成任务，不为并发而重复请求。 |

普通聊天及 ASMR 覆盖 Fish REST、Fish MCP、百炼/Qwen、通用 TTS、MiMo。CosyVoice 本地后端使用单实例与原生互斥锁，继续一次生成一段，但可与前一段播放重叠。

通话沿用现有 Fish REST/MCP 两种服务，本次不增加其他服务的通话支持。Android 和 Windows 共用 Dart 调度代码；平台能力限制保持原有行为。

## 并发边界

- 这是每个活动播放流程的有界预取，不是一次提交整段长回复，也不是跨所有设置页的全局限流器。
- 后段先返回时保留结果，按原始顺序播放；主聊天的演出分发仍跟随实际播放段落。
- Studio 同一模型与音色复用项目初始化，每段使用独立文本块、独立费用预估与生成结果校验。
- 电话预取层保留首块流式输出和背压，后续文本等待队列名额；挂断、打断、切存档会停止准入并取消未消费的流。
- 普通聊天/ASMR 取消后不再提交新段，晚到文件清理。已提交的云端请求不保证撤销或退款。
- 一个片段质量失败时，先等待已提交片段的结果，再决定是否补充；连续两个异常片段停止，避免继续预取第三段。

## 限流与重试

收到 429 后，本轮停止扩展请求，该 provider 在当前应用进程中的后续批次降到一路。应用重启后恢复默认并发上限。此策略没有自动重发被限流的片段。

Fish REST、通用 TTS、MiMo 的生成 POST 改为单次提交，网络中断或超时不会自动重复潜在计费请求。Fish MCP 和通话仍保持原有的不重试生成原则；Qwen 生成链路维持原有单次提交。单纯音频下载可保留其下载重试。已明确获得但质量不合格的 REST 音频仍沿用原有质量重生成预算，MCP 不重生成。

Windows 仍先探测直连/代理；实际 POST 中断后，本次显示失败，下一次显式请求可走已重新选择的代理路径，不为切代理重放结果未知的 POST。

临时音频文件使用微秒时间与进程内序号，避免同一毫秒返回的不同段覆盖同一文件。

## 验证

相关 18 个测试文件共 381 项通过；修改文件静态分析无问题。测试使用本地模拟服务、模拟 MCP 工具和原生音频桩，没有发送真实计费请求。

覆盖两路请求启动、乱序返回、顺序播放、首块流式输出、三段缓冲容量、停止与晚到文件清理、异常停止准入、429 降并发、Studio 文本块隔离、电话打断后恢复收音、只记录实际播完的句子、立体声设置在同轮保持一致及代理失败不重放。

测试日志：`build/tts-parallel-final-tests.log`。实机播放与服务端实际并发吞吐仍需后续安装验收；本地通过不代表服务商会同时执行两项任务。

核心实现：`lib/src/speech_preparation.dart`、`lib/src/realtime_call/call_speech_prefetch.dart`；接入点：`chat_screen.dart`、`continuous_asmr_page.dart`、`realtime_call/call_session.dart`。
